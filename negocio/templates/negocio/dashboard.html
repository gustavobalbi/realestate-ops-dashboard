Sobre os dados: Empreendimentos

Alimentada por empreendimentos, unidades, vendas e obra_andamento.

Critério de "venda ativa": data_distrato é a fonte de verdade, nunca status_venda sozinho. Achado de qualidade de dados: de {{ achados_vendas.vendas_com_distrato }} vendas com data_distrato preenchida, {{ achados_vendas.status_desatualizado }} ainda tinham status_venda = "ativa" — o sistema de origem falhou em atualizar esse campo no distrato. Por isso uma venda só conta como ativa quando LOWER(TRIM(status_venda)) começa com "ativa" e data_distrato IS NULL: {{ achados_vendas.vendas_ativas }} de {{ achados_vendas.total_vendas }} vendas cadastradas.

Mesmo achado em unidades.status: as {{ achado_cancelado.total_cancelado }} unidades com status bruto "Cancelado" têm, todas, uma venda vinculada com status canônico "Distrato" ({{ achado_cancelado.total_com_venda_distrato }} de {{ achado_cancelado.total_cancelado }}) — são duas grafias históricas para o mesmo evento, não duas categorias reais, então norm_status_unidade() funde as duas no mesmo bucket "distrato" (ver negocio/normalize.py; visível também como filtro único na tela Dados).

Velocidade de vendas = vendas ativas ÷ total de unidades ofertadas, por empreendimento.

Risco de estouro de custo = soma(custo_realizado_mes) − soma(custo_orcado_mes) em obra_andamento, acumulado por empreendimento; só entram os que estouraram (resultado positivo).

Sobre os dados: Clientes

Alimentada por clientes (perfil, cidade, uf, e-mail) e vendas.

Critério de contagem: cada cliente é identificado pelo e-mail normalizado (minúsculo, sem espaços/acentos) — evita contar duas vezes o mesmo cadastro caso ele se repita na base.

Há indícios de cadastros duplicados? Não. A base tem {{ duplicidade.total_clientes }} clientes cadastrados e {{ duplicidade.emails_distintos }} e-mails distintos — mesmo número, mesmo depois de normalizar caixa e espaços. Isso descarta duplicidade real de cadastro.

O que existe são {{ duplicidade.homonimos|length }} grupos de homônimos: pessoas diferentes que compartilham o mesmo nome, geralmente distinguíveis pela cidade de cadastro. Se a análise fosse feita ingenuamente por nome — tratando homônimos como se fossem a mesma pessoa — o número de "clientes únicos" cairia artificialmente e o ticket médio por cliente subiria de forma equivocada, de R$ {{ duplicidade.ticket_medio_correto|floatformat:0 }} para R$ {{ duplicidade.ticket_medio_ingenuo_por_nome|floatformat:0 }} nesta base — distorcendo a métrica justamente na direção oposta à que uma duplicidade real produziria.

Sobre os dados: Vendas

Alimentada só por vendas, filtrada por data_distrato IS NULL ({{ achados_vendas.vendas_ativas }} de {{ achados_vendas.total_vendas }} linhas).

Diferença em relação à aba Empreendimentos: aqui o critério é literal sobre a coluna (só data_distrato); em Empreendimentos usamos a regra mais completa, que também exige status_venda = "ativa" (ver o ícone daquela aba). Na prática as duas definições coincidem nesta base: as {{ achados_vendas.status_desatualizado }} linhas com status_venda desatualizado têm data_distrato preenchida, então nunca entram aqui de qualquer forma.

Achado na direção oposta: {{ achados_vendas.distrato_sem_data }} linhas têm status_venda canonicamente "distrato", mas data_distrato NULA — aqui o status já está certo, só falta a data (o sistema de origem não registrou quando o distrato aconteceu). Na tela Dados (aba Vendas), a coluna STATUS já mostra o resultado da regra acima (não o texto bruto — nas {{ achados_vendas.status_desatualizado }} linhas do primeiro achado ela aparece "DISTRATO" mesmo com o texto bruto dizendo "Ativa"), e a coluna DATA DE DISTRATO mostra "SEM REGISTRO" nas {{ achados_vendas.distrato_sem_data }} linhas deste segundo achado, em vez do "--" genérico (que ali sempre significa "venda ainda ativa").

Os gráficos de período, forma de pagamento e tipo de unidade somam apenas essas vendas ativas; o mapa e os dois primeiros gráficos se re-filtram ao clicar num empreendimento no mapa.

Sobre os dados: Financeiro

Alimentada só por financeiro_mensal ({{ resumo_financeiro.total_linhas }} linhas, {{ resumo_financeiro.total_meses }} meses, {{ resumo_financeiro.total_empreendimentos }} empreendimentos).

Resultado recalculado = receita_reconhecida − custo_incorrido − despesas_corporativas_rat. Uma linha é "inconsistente" quando esse valor difere de resultado_reportado em mais de R$ 0,01 (tolerância de arredondamento).

Achado: {{ resumo_financeiro.total_inconsistentes }} de {{ resumo_financeiro.total_linhas }} linhas são inconsistentes, atingindo {{ resumo_financeiro.meses_inconsistentes }} dos {{ resumo_financeiro.total_meses }} meses e {{ resumo_financeiro.empreendimentos_inconsistentes }} dos {{ resumo_financeiro.total_empreendimentos }} empreendimentos — uma diferença acumulada (em módulo) de R$ {{ resumo_financeiro.magnitude_acumulada_abs|floatformat:0 }}.

Hipótese mais provável (a confirmar): lançamento de custo ou despesa em competência diferente da do relatório já publicado (ajuste retroativo não refletido no número reportado), ou uma rubrica que entra no cálculo de resultado mas não está representada nas colunas desta tabela.

Sobre os dados: Obra

Alimentada por obra_andamento e empreendimentos.status. Esta seção não responde a uma das 4 perguntas do briefing -- é uma investigação à parte sobre o resto dessa tabela: custo_orcado_mes/custo_realizado_mes já alimentam "Risco de estouro de custo" na aba Empreendimentos; aqui entram percentual_conclusao (não usado em nenhuma tela até então) e status (idem).

As colunas de custo desta tabela entram na validação financeira (pergunta 4)? Investigado: cruzando as 562 linhas de obra_andamento com as 562 de financeiro_mensal por (empreendimento_id, mes_referencia), a chave bate 100% dos dois lados, e financeiro_mensal.custo_incorrido é exatamente igual a obra_andamento.custo_realizado_mes nas 562 linhas (diferença zero em todas). Ou seja: o "custo incorrido" que entra no recálculo da pergunta 4 já é esse mesmo número, só duplicado em duas tabelas -- não há uma inconsistência escondida nessa relação para reportar.

percentual_conclusao bate com empreendimentos.status? Investigado e a resposta é não — checagem feita, sem achado sólido: a média de conclusão (medição mais recente por empreendimento) é praticamente igual entre status {% for m in achado_conclusao_status.por_status %}"{{ m.status }}" {{ m.media_percentual|floatformat:1 }}%{% if not forloop.last %}, {% endif %}{% endfor %}, sem nenhum padrão que separe uma categoria da outra (o único empreendimento em "Lançamento" — por definição, obra ainda não iniciada — aparece com a maior média das quatro). Por isso esta aplicação não usa percentual_conclusao pra validar/sinalizar nada sobre status. Observação à parte, checada pelo mesmo motivo: {{ achado_conclusao_status.em_obras_ha_mais_de_1_ano }} empreendimentos estão "Em obras" há mais de um ano desde o lançamento (o mais antigo, {{ achado_conclusao_status.em_obras_idade_maxima_anos|floatformat:1 }} anos) — sem um segundo sinal que bata (como o % de conclusão, acima), não dá pra confirmar se é obra realmente parada ou só um projeto grande, então não vira "erro" nem tratamento.
